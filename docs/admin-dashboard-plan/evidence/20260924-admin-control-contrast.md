# 2026-09-24 local admin contrast follow-up

This records local working-tree evidence only. The contrast and QA-harness changes in this follow-up have not been deployed.

- Added `axe-core` 4.13.0 to the development QA harness and ran its WCAG AA `color-contrast` rule against the rendered admin shell across all 11 admin sections in Light and Dark: 22 audits, zero violations, and zero incomplete results.
- Corrected dark-theme primary action and selected-pagination colors after the rendered scan found white text on blue backgrounds below 4.5:1. The selected navigation item now also has an inset primary-color bar so its state is not conveyed by color alone.
- Strengthened shared form-field, secondary-button, pagination, cancel-button, and danger-button boundaries for Light and Dark themes. A rendered browser audit compared visible enabled button/input/select/textarea fills and borders against their surrounding backgrounds at the WCAG 2.2 3:1 non-text threshold: 22 section/theme audits, zero findings.
- The non-text audit is deliberately scoped to interactive-control fills/borders. It does not establish coverage for every icon, chart, graphic, status outside the shared badge component, or browser-native visual, and it is not a substitute for manual or assistive-technology review. Automated text contrast also does not establish overall accessibility conformance.
- Additional customer-support-widget contrast follow-up (local only): the first rendered dark-theme scan found a 3.67:1 white-on-blue primary action. The action now uses a darker dark-theme blue and an opaque slate disabled state; the dark-theme close glyph also has a stronger color. The decorative close glyph is `aria-hidden`, so axe's text-contrast “incomplete” result for that single character is excluded from text findings and its rendered foreground/background contrast is checked separately at the 3:1 non-text threshold.
- The authenticated local support/admin browser matrix passed in Chromium, Firefox, and WebKit. Each engine ran two widget text-contrast audits and two close-control contrast audits (Light and Dark), plus 22 admin text-contrast and 22 interactive-control boundary audits, all with zero findings/incomplete results. Keyboard-target counters were 468 in each engine; Chromium's isolated headed actual per-tab 200% zoom run passed 22 section/theme checks with no overflow and visible focus. All passing runs had zero console/page errors. One WebKit attempt produced a single transient local admin-api access-control page error; its immediate isolated rerun passed, with no CORS changes made.
